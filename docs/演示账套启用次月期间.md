# 演示账套启用次月期间

## 背景与目标

GUI 冒烟用例「固定资产次月起提、待摊当月就摊」长期失败：
演示账套结完演示月份后**只留一个 open 期间**，资产登记进当月后，
「次月计提」这一步没有可记账的期间，走到计提就报「期间未启用」。

这不是测试环境独有的问题：真实用户在演示账套里登记一张固定资产，
点「计提」同样会撞上「下一期间未启用」，要么先结账才能看到折旧 ——
演示账套的意义恰恰是「不用结账也能逛一圈」。

## 技术方案

1. `CreateDemoBook` 在结完前 toMonth−1 个月之后，调用
   `PeriodRepo.EnsureNextOpen(toMonth)` 把 toMonth+1 月置为 open。
   - 与「结账自动启用下期」是同一个动作，不引入新规则；
   - toMonth=12 时由 EnsureNextOpen 的跨年分支补出次年期间行再启用。
   - 两个 open 期间并存不违反约束：`NewCalendar` 建账时本身就会把
     ≤ 当前月的期间全部置 open。

2. CLI `miniaccount demo` 收敛到 `svc.CreateDemoBook`。
   现在 CLI 与界面是**两份** create→seed→close 的实现
   （注释声称共用，实际没有），次月启用加在一处才能两边同时生效；
   顺手消除漂移风险（公司名、企业规模两处已经不一致）。
   - CLI 保留 `--force` 删除与「已有账套」的友好报错，然后再调
     CreateDemoBook；进度打印改用 `DemoResult` 的字段。

## 涉及模块

- `internal/service/demo.go` — CreateDemoBook 收尾处启用下期
- `cmd/miniaccount/helpers.go` — cmdDemo 改为调 CreateDemoBook
- `desktop/demo_test.go` — 回归断言：演示账套应有「当前月 + 次月」
  两个 open 期间

## 边界

- toMonth=12：启用次年 1 月（EnsureNextOpen 自动补期间行）。
- 已有账套：CreateDemoBook 依旧拒绝，CLI 的 `--force` 流程不变。
- 关闭期间失败走 Warnings 的逻辑不变；次月启用失败同样记入
  Warnings 而不是中断生成（演示数据已写完，提示即可）。

## 实施中连带修掉的测试侧问题

修完演示账套后跑全量 GUI 冒烟，暴露出三处**测试自身**的脆弱点，
与产品代码无关，一并修复：

1. **jsdom 环境缺 localStorage**（`gui.test.mjs` boot 阶段）
   Node ≥25 在 globalThis 上自带 Web Storage 桩，
   「只补缺」的全局拷贝循环把它跳过，界面里的 localStorage 解析到
   Node 桩上、一碰就抛 —— App 的 mounted 钩子死在 refreshBook 之前，
   界面永远停在「尚未打开账套」。现对 localStorage/sessionStorage
   强制使用 jsdom 实现。

2. **「结账」被子串匹配误伤**（两条用例）
   `page.click('结账')` 按子串找按钮，而「反**结账**」也命中；
   最后一个已结账期间的反结账按钮在 DOM 顺序上排在「结账」前面。
   四条结账/反结账点击全部改 `clickExact`。

3. **用例依赖「恰好两个连续 open」的账套状态**
   - 固定资产用例原来断言 `opens >= 2`，但套件前面有真·结账用例，
     而反结账会把后面的启用期退回 future —— 无论演示账套预启用几个，
     跑到这里都可能只剩一个 open。改为自给自足：**自己把当月结掉**
     来启用次月再计提，这才是真实的记账顺序（想记次月的账，
     先把这个月结掉）。
   - 底稿/证据链/三个税务用例原来取 `opens[last]`，但页面的期间
     下拉默认选中 `opens[0]`（当前账期），离开再回来选择丢失。
     统一改为 `opens[0]`。
