## 批 A：数据完整性（附件隔离 / 并发双凭证 / 恢复验证 / 草稿删档）

### A1. 附件目录按账套隔离

**现状**：`Service.FilesDir()` 返回 `<db目录>/.files`——同目录所有
账套共享。备份遍历整个 `.files` → A 的备份混入 B 的附件；恢复时
`stashExisting` 挪走共享目录 → B 附件物理丢失。

**方案**（backup.go:12 注释里 `公司名.files/` 的原设计）：

- `FilesDir()` 改为 `<db去掉扩展名>.files`（`公司A.db` → `公司A.files`），
  与 db 同目录、按账套名天然唯一。
- `service.Open` 后做**惰性迁移**：扫描 `attachment`/`attachment_v2`
  两表引用的 `sha256`，新目录缺失而旧 `.files` 存在的文件**复制**
  过去（不移动——同 hash 内容可能被同目录其他账套引用）。迁移只做
  一次：用「新目录存在」作标志，或每次启动跑但只补缺（幂等）。
- 备份/恢复不用改：`collectFiles`/`stashExisting`/解压都只经
  `FilesDir()` 参数，按账套隔离自然生效。归档内相对路径
  （`<hash前2位>/<hash>`）格式不变，老备份仍可恢复。
- 遗留 `.files` 目录不删（可能还有其他账套的文件）。

### A2. 生成凭证的并发双写

**现状**：`PostInvoice`/`PostClaim`/`PostRun` 都在 `WithTx` **之前**
检查状态，事务内的 UPDATE 无条件覆盖。并发两连接 → 两张草稿，
单据只指向最后一张，结账两张都过账。`PostClaim` 甚至连前置状态
检查都没有（只靠 `BuildEntries` 要求 `approved`）。

**方案**（对齐 `PostFlows` 已有的「事务内复查」模式）：

- `PostInvoice`：事务内 `UPDATE invoice SET voucher_id=?, status='booked'
   WHERE id=? AND voucher_id IS NULL` → 0 行 → `ErrConflict: 已生成凭证`。
- `PostClaim`：同法 `WHERE id=? AND voucher_id IS NULL`。
- `PostRun`：`UPDATE salary_run ... WHERE id=? AND status='draft'` →
  0 行 → `ErrRunNotDraft`。
- 前置检查保留（早报错友好），事务内条件更新是正确性防线；
  条件不命中时整个事务回滚，已建的草稿凭证随之消失。

### A3. 恢复先验证后生效

**现状**：`backup.Restore` 内部有完整的 stash→unstash 回滚，但
「新库能否打开」的验证在函数返回**之后**（`service.Open`），
失败时原账套已进 stash，桌面端报错，用户手工找文件。

**方案**：把验证收进 `Restore` 的 `success` 守卫之内：

- 签名加 `verify func(ctx context.Context, dbPath string) error`
  （backup 不能 import service，回调注入）。
- 时序：解压+校验 hash+rename 落位后 → `verify(dbPath)` →
  失败走 defer unstash 回滚原账套；通过才解附件、置 success。
- `service.Restore` 与 `App.RestoreBackup` 都传同一个验证器：
  `sqlite.PeekBook`（只读打开、跑版本检查，不迁移）——版本
  过新/文件损坏都在回滚保护内报出来。

### A4. 删除草稿时解除生成单据的关联

**现状**：`DeleteDraft` 只清 `attachment` 关联就删 voucher；
`invoice`/`expense_claim`/`bank_flow`/`salary_run`/
`asset_depreciation`/`amortization_entry`/`ai_suggestion` 均
`REFERENCES voucher(id)` 无级联 → FK 报错，界面无解除手段。
（`voucher_entry` 有 CASCADE、`audit_adjustment` 有
`ON DELETE SET NULL`，不用动。）

**方案**：`DeleteDraft` 事务内按来源类型分别处理：

| 引用方 | 处理 |
|---|---|
| `invoice.voucher_id` | `SET voucher_id=NULL, status='verified'`（booked→回到已认证，可重新生成） |
| `expense_claim.voucher_id` | `SET voucher_id=NULL, status='approved'`（posted→回到已审批；`BuildEntries` 只允许 approved，故上一态确定） |
| `bank_flow.voucher_id` | `SET voucher_id=NULL, status='matched'`（posted→回到已匹配） |
| `asset_depreciation`/`amortization_entry` | `SET voucher_id=NULL`（计提行回到可重新生成态） |
| `ai_suggestion.final_voucher_id` | `SET voucher_id=NULL` |
| `salary_run.accrual/payment_voucher_id` | **拒绝删除**：工资凭证请在工资页处理（孤儿化工资单的后果比禁止删除大） |

审计 detail 里记录解除了哪些单据关联。

## 批 B：账务正确性（工资重算 / 对账余额 / 进项抵扣 / 部门引用 / 结账预览）

### B4. 工资重算后后续月份不更新

两个症状，一个根源「重算不传导」：

- **汇总列不更新**（小修）：`SaveRun` 覆盖草稿的 UPDATE 只写
  `status/tax_table_json/updated_at`，`total_gross` 等只在 INSERT
  写。补进 UPDATE 列。
- **后续月份不级联**（主修）：一月重算后，二月已存 items 的
  累计税基已变（累计预扣是年度累计制），二月 run 与其已生成
  草稿凭证都带着旧数。
  **方案**：`SaveRun` 覆盖草稿后同事务级联——对同年更晚月份
  已存在的 run，按月升序：
  1. 用其 `salary_item` 已存输入字段（base_salary…other_tax_
     deduction、si_base/hf_base、insurance_overridden）重建
     `BuildRunInput.Amounts`——手工调整**持久化在 item 行里**，
     不会丢；人员构成按「该 run 已有 item」保持（不增不删）。
  2. 经 tx 内 querier 版 `buildRunQ`（`priorYTD` 已收 querier，
     `BuildRun` 需抽出 q 参数版本）重算 items+合计并覆盖。
  3. 该 run 有 accrual/payment 凭证且仍是 `draft` → 用
     `run.BuildAccrualEntries`/`BuildPaymentEntries` 重出分录，
     `SaveDraftInTx`（同 voucher id，Generated）覆写行；
     凭证非 draft → 跳过并记警告。
  4. 某月重算失败 → **停止级联**（其后月份累计基准已不可信），
     警告注明卡在哪月。
  `SaveRun` 返回 `SaveRunResult{ID, Recalced []string, Warnings
  []string}`，service 透传给界面（「已联动重算 N 月」toast）。
- `PostRun` 并发防线见 A2。

### B5. 银行流水余额「未知即 0」与未达账项口径

- **balance 存 NULL**：schema 列本就 nullable，对账查询也写了
  `balance IS NOT NULL`——但 INSERT 写 `int64(f.Balance)` 把
  未知落成 0，NULL 设计被写入侧废掉。`bank.Flow` 加
  `BalanceKnown bool`（不改 `Balance money.Money` 类型，
  dedup hash 输入不变、兼容存量）；无余额列的导入置 false →
  列存 NULL。扫描处 `sql.NullInt64` 读取。之后：
  - `openingBalance` 反推只用 `balance IS NOT NULL` 的流水
    （SQL 已挡），全未知 → 期初报「无法推断」而非按 0 判不平；
  - 期初推不出时调节表给「期初未知」标识，不拿 0 当真值判差。
- **未达账项口径**：`flowsNotBooked` 的 `voucher_id IS NULL`
  改为「无凭证或凭证仍是草稿」
  （`OR EXISTS(SELECT 1 FROM voucher v WHERE v.id=f.voucher_id
  AND v.status='draft')`）——草稿未过账、账面未变，流水就仍
  是未达。`bank_flow.status='posted'` 在生成草稿时就被置位
  的语义不动（结束态一致），只修对账口径。

### B6. 进项专票抵扣与认证链、纳税人身份

**现状**：新发票默认 `pending`（未认证）；`PostInvoice` 只看
`DeductibleTax()>0`（按票种）就出进项税分录——未认证专票
照样生成；小规模账套没有可过账进项税科目 → 被自家校验拒。

**方案**（`PostInvoice` 进项分支加两道门）：

- **认证门**：进项专票（`DeductibleTax()>0`）要求
  `status='verified'` 才生成，`pending` → 报错
  「专票未认证，请先在发票页认证」——落实
  `pending→verified→booked` 设计链。普票不受影响
  （`DeductibleTax=0`，pending 可直接生成）。
- **身份门**：按开票日期在 `vat_status_history` 取当时
  纳税人身份（无历史取 `book.vat_status`）：`small_scale`
  → 进项税不可抵扣 → 不出进项税分录、全额入成本；
  `general` → 照旧出分录。

### B7. 部门删除漏查草稿

`DepartmentUsageOf` 数 `ledger_entry`（只含已过账）→ 草稿
引用不计。改为数 `voucher_entry`（含草稿+已过账一体，
`contact` 的同款做法、注释就在 contact.go:126）。

### B9. 结账预览=真结账干跑

**现状**：`PreviewClose` 走 `Plan`（只读已过账总账）；真结账
`ClosePeriod` 先 `PostPeriodDraftsInTx` 再算结转 → 预览与实际
两套数字。

**方案**：预览直接复用真结账路径、事务回滚：

- `ClosePeriod` 抽出 `closePeriodTx(ctx, tx, in)`（含过账草稿、
  结转计划、建结转凭证、关期间——全部 tx 内动作）；
- 新 `ClosingRepo.DryRunClosePeriod`：`WithTx{ closePeriodTx →
  返回哨兵错 errDryRun }`，成功结果随哨兵带回、整体回滚；
- `PreviewClose` = 体检（照旧单独跑，事务里跑不了）+
  `DryRunClosePeriod` → 预览拿到的就是真结账会发生的全部
  数字（草稿过账失败也在预览时报错，等于白赚一道预检）。
  `ClosingPreview` 补 `postedDrafts` 字段。

## 追加修复（验收复现的 7 项，2025-11 第二轮）

1. **旧账套附件迁移查错表名**：`migrateLegacyFilesDir` 查的是
   `attachment_v2`，但迁移 0013 已将其改名为 `attachment` ——
   UNION 查询必败、直接 return，旧 `.files` 内容没有迁入。
   改查现行表名 `attachment`。

2. **工资级联账表背离 + 过期草稿照旧过账**：
   - `cascadeAfter`/`recascadeRun` 增加冻结守卫：工资单任一
     关联凭证已过账（或非草稿）时**整个 run 不再改写**，只加
     `Warnings` —— 只改工资单不改已过账凭证就是账表背离；
   - 新增 `Vouchers().RegenStaleDraftVouchers(period)`：
     对当期所有「关联工资单」的**草稿**凭证，按工资单最新数据
     在事务外准备、事务内整组重写（先删 `voucher_entry` 再插）。
     接线到 `PostPeriodDrafts`/`PostPeriodDraftsInTx`/
     `DryRunClose`（预览同样按新数算）—— 级联没改到的旧凭证
     在过账一刻被刷新，结账不可能再按旧税额入账；
   - `Payroll.vue` 展示 `SaveRun`/`BuildRun` 返回的 warnings
     （`res.warnings` 逐条 notice）。

3. **恢复验证仍不够真**：`VerifyOpenable` 原为只读开库 +
   user_version 判定 —— 缺迁移记录但校验和正确的库照样通过。

   凭证的派生记录，随凭证删除而消失；删除后可重新计提）。
